### P0-004 · [grad-gate] The `bf` (backfill) flag on /api/track has zero legitimacy check, letting anyone defeat the grad-gate's only real anti-farm control and trigger automated treasury-signed diploma mints
- **Where:** `lib/school-progress.js:173` · auth-bypass
- **Evidence:** server.js:17118-17119: `const m = /^lesson_complete:([a-z0-9-]{1,48})$/.exec(...); if (m && b.sid) schoolProgress.mark(b.sid, m[1], { backfill: b.bf === 1 || b.bf === "1" });` — bf comes straight from the POST body with no auth, no session-age check, no proof it's a real pre-gate learner. lib/school-progress.js:173-178: `const backfillCovers = now < BACKFILL_SUNSET && marks.length - live.length > 0; if (liveBuckets < minSpreadBuckets && !backfillCovers) { return {ok:false, code:'burst', ...} }` — a single bf:1 mark anywhere in the session waives the ENTIRE spread requirement for all marks, live or not. ### P0-005 · [persistence] kvstore.js treats a corrupt app-state.json as a healthy, persistent, empty store — silently wipes every kv-backed ledger and reports success on the next write
- **Where:** `lib/kvstore.js:19` · correctness
- **Evidence:** (function load() { try { fs.mkdirSync(DATA_DIR, { recursive: true }); persistent = true; if (fs.existsSync(FILE)) { const o = JSON.parse(fs.readFileSync(FILE, "utf8")); ... } } catch (e) { console.warn(`[kvstore] volume unavailable (${e.message}) — running in-memory only`); } })();  -- `persistent = true` (line 22) is set BEFORE the JSON.parse that can throw (line 24), and the catch block (line 29-31) never resets it. Reproduced directly: `echo '{not valid json' > app-state.json; DATA_DIR=... node -e 'require("./lib/kvstore.js")...'` printed the misleading log `volume unavailable ... running in-memory only`, yet `kv.isPersistent()` returned `true`, a pre-existing key was gone (`MISSING`), and `kv.setVerified("newKey","newValue")` returned `true` while overwriting the on-disk file to `{"newKey":"newValue"}` — permanently destroying every previously-stored key with no quarantine/backup (sigstore.js explicitly does the split-and-quarantine fix for this exact class of bug in its own load(); kvstore.js never got it). The same anti-pattern (persistent=true set, then an un-recovered JSON.parse in the same try/catch) is also present in lib/credentials.js, lib/grad-tracker.js, lib/jupverify-intake.js, lib/recap.js and lib/school-progress.js.
- **Impact:** server.js's own CUNA payout "storage" hard-check (server.js:12237, `add("storage", kv.isPersistent(), ...)`) exists specifically so an operator never confirms/sends a payout batch when records can't survive a restart — but this bug makes `isPersistent()` return true immediately after a corruption event that just destroyed the whole CUNA_PAID_KV/CUNA_BATCH_KV/CUNA_STAKE_DAYS_KV/BUYCOMP_KEY history. Concretely: a Railway SIGKILL mid-write (the file the code's own atomic-write.js comment says happens "on every redeploy") or the tmp-file race described in the next finding leaves app-state.json corrupt; on the next boot kvstore silently starts from empty state but claims persistent=true; any subsequent kv.set/setVerified call (including a legitimate payout confirm) overwrites the file with the new, now-incomplete state, and the operator sees green checks throughout. Previously-paid CUNA batches, arm flags, ratchet overrides and buycomp payout records are gone with no error surfaced anywhere.
- **Fix:** In lib/kvstore.js, mirror lib/sigstore.js's load(): separate the mkdirSync (sets persistent=true) from the JSON.parse (only updates `state` on success), and on a parse failure, copy the corrupt file aside (e.g. `${FILE}.corrupt-${Date.now()}`), set `persistent = false`, and log loudly that persistence is disabled until an operator restores the file — never silently proceed as if the volume were fresh. Apply the same fix to lib/credentials.js, lib/grad-tracker.js, lib/jupverify-intake.js, lib/recap.js and lib/school-progress.js, which share the identical bug.

### P0-006 · [persistence] CUNA payout batch EXPORT writes with plain kv.set, not setVerified — inconsistent with confirm/void/sweep on the same money path
- **Where:** `server.js:12423` · correctness
- **Evidence:** if (!batch.count) { note = ...; } else { batches = { ...batches, [id]: batch }; kv.set(CUNA_BATCH_KV, batches); created = { ...batch, airdropLines: pay.toAirdropLines(batch.amounts, 9) }; console.log(`[cuna-payout] batch ${id} created — ${batch.count} wallets, ... - **Impact:** The code's own design comment two lines above this block says "exporting again cannot offer the same money twice" — that guarantee depends entirely on the export write reaching disk. The success response (`created`) is still returned to the operator, who may proceed to sign the actual on-chain airdrop believing the batch is durably held. If the process restarts before the write reaches disk, the batch record vanishes, the exported amount reverts to "owed" in the next preview, and a second export/payout of the same money becomes possible — the exact double-pay scenario the module's docstring says this bookkeeping exists to prevent.

### P0-011 · [tools-money] SEND PRIZES resends the full, unfiltered recipient list on every click — a retry after a partial failure double-pays already-sent winners

### P0-012 · [tools-money] Hatchery treats an ambiguous confirmation timeout as a plain failure and lets the user immediately retry, minting a second token and paying the fee again
- **Where:** `public/hatchery.html:619` · correctness
- **Evidence:** confirmTx() (lines 619-630) throws the same generic `Error('Timed out waiting for confirmation — check Solscan')` whether the transaction failed or is merely slow to confirm, and doHatch()'s catch block (lines 838-843) does `showError('Hatch failed: ...')` then `finally { btn.disabled = false; }` — no distinction between 'failed' and 'unconfirmed', and no signature is surfaced to check before retrying. Server-side, /api/hatchery/build (hatchery.js:501-556) does `Keypair.generate()` (hatchery.js:272) for a brand-new mint on every call, so there is no way to resume the original attempt.
- **Impact:** locker-room.html's own comment (lines 771-774) documents exactly this risk elsewhere in the same codebase ('a blind one-click retry here would create a SECOND lock... flag it as unconfirmed, NOT safe-to-retry') and disables retry on timeout (line 837). Hatchery has no equivalent, so a slow-but-landed mint transaction looks identical to a hard failure and invites an immediate, costly retry.
- **Fix:** Mirror the locker-room pattern: distinguish a hard on-chain failure (`s.err`) from a timeout in confirmTx(), surface the signature and a Solscan link in the error message, and on timeout disable HATCH (or relabel it 'Reload to retry') instead of silently re-enabling it.

### P3-152 · [tools-safety] isNft heuristic misclassifies any real fungible token held in a single whole unit with 0 decimals, permanently blocking it from Firepit's burn/reclaim
- **Where:** `public/firepit.html:397` · correctness
- **Evidence:** function burnable(a){ return !a.frozen && !a.isNft; }  with isNft set server-side as  isNft: a.decimals === 0 && a.uiAmount === 1  (server.js ~13271)
- **Impact:** A 0-decimal fungible SPL token (some memecoins and reward tokens use 0 decimals) held with a balance of exactly 1 is indistinguishable from an NFT by this heuristic and gets tagged 'NFT · soon', its checkbox is never rendered, and the user can never burn it or reclaim its rent through this tool even though it is ordinary junk. This is the safety-conservative direction (never burns something that might be an NFT), so it's arguable whether it counts as a bug versus an accepted false positive — flagging for visibility since the copy ('NFT floor-price safety is coming') implies it's confident about NFT detection when it isn't.
- **Fix:** If a real disambiguation signal is available (e.g. checking the mint's supply/decimals more thoroughly, or a Metaplex/Token-2022 NFT flag) use it instead of the (decimals===0 && uiAmount===1) heuristic; at minimum, soften the tag to 'possible NFT' rather than an unqualified 'NFT'.
