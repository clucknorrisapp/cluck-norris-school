# Hub load proof — 50 x 200 — 2026-09-18

Colosseum roadmap §15 EE3 ("Load proof for the public reads"). One machine's numbers, taken with
`scripts/hub-load-fixture.cjs` + `scripts/hub-load-smoke.cjs` against the default fixture (50
registered Hub projects, ~50 wallets each, 30 days of accrual, ~4 sent lock-to-earn batches per
project — 9,832 real receipts, every one reproducible: `/api/hub/load-0/reproducibility` reports
`{"total":52,"reproduced":52}` for the first project, and the same 1:1 ratio holds project to
project). Nothing here is a claim about production traffic or about any other machine — it is
what this box measured, on this tree, on this day.

## The box

- `nproc`: 4
- `node -v`: v22.22.2
- RAM: ~16 GB (`MemTotal` from `/proc/meminfo`)
- OS: Linux, x86_64

## The fixture

```
$ node scripts/hub-load-fixture.cjs
fixture: 50 projects x ~50 wallets, 9832 receipts across 4 batches/project
app-state.json: 6.99 MB (7326689 bytes)
elapsed: 0.28s
```

Well inside the 60s budget the roadmap item sets for a 50x200-class fixture — building it is not
the expensive part of this exercise; serving it under load is.

## What was driven, and how

`scripts/hub-load-smoke.cjs` boots the real `server.js` against that fixture and, for each route
below, fires (a) one cold request, (b) one warm request (repeat, same synthetic IP), then (c) a
burst of 70 parallel requests from that same synthetic IP — each route gets its OWN synthetic
`CF-Connecting-IP` so the eleven routes' traffic cannot exhaust each other's rate-limit buckets and
confound the reading. Concurrently, for the whole run, `/healthz` is polled every 100ms and the
worst latency observed is reported separately — this is the literal P1-03 number
(`docs/HUB_PUBLIC_SURFACES_VERIFY_2026-09-18.md`: "ten unauthenticated requests… take `/healthz`
from sub-millisecond to ten seconds").

## Which routes were limited, and which were not, on this tree today

This tree is `claude/colosseum-batch-13` merged onto this worktree, **before** the concurrent
DD5/P1-03 fix round (rate limiter + per-project cache on the four flagged routes) has landed here.
That is exactly what the table shows:

- **No `hubheavy` rate limiter today** (confirmed by reading `server.js` before this exercise —
  `rateLimit("hubheavy", …)` is absent from all three): `GET /api/hub`, `GET
  /api/hub/wallet/:wallet`, `GET /api/hub/:project`. Same for the `GET /hub/:project` share page.
  All four show **zero 429s** even under a 70-wide burst — nothing refuses the load — and three of
  the four blow the 500ms budget outright. `/api/hub` and `/api/hub/wallet/:wallet` are the worst:
  a wallet lookup or a full listing walks every registered project's `hubProjectView()` (the
  per-receipt `explanation` attribution over every accrual slice), and 70 of those landing
  together serialise on Node's one event-loop thread — the burst's own p95 (50.8s and 57.2s) is
  effectively "70 x roughly the per-call cost," because nothing lets a second request start before
  the first finishes its CPU-bound walk.
- **Already `rateLimit("hubheavy", { windowMs: 60000, max: 60 })`-gated**: reproducibility, its
  history, standings, the bundle, the badge, both feeds. Every one of these shows exactly **12
  429s** — cold + warm + 70 burst = 72 requests from one IP against a 60/min ceiling refuses the
  last 12, precisely as the limiter is supposed to. The limiter is doing its job on volume.
- **But the limiter alone does not bound latency under load.** Three of the seven already-limited
  routes (`batch/:batchId/bundle`, `feed.json`, `feed.xml`) still land the *successful* 58 requests
  at ~1-2 seconds p95 on this fixture, because each one independently recomputes
  `hubProjectView()`/`hubReproducibilityFor()` for its one project rather than sharing the
  reproducibility route's own 5-minute in-process cache (`HUB_REPRO_CACHE` in `server.js`). The
  badge route is the exception among the limited set (17-28ms) — it goes through
  `hubReproducibilityFor()` too, but for a small project that computation is cheap; the other three
  routes' extra per-request cost (rebuilding the full public project view, or the feed items on top
  of it) is what pushes them over budget even while correctly rate-limited.
- **Cache behavior observed**: `/api/hub` (list) shows a lower warm-vs-cold ratio (773 vs 871ms)
  consistent only with `Cache-Control: public, max-age=60` — a *browser* cache hint this script's
  bare `fetch()` never honors, not a server-side memoization; the small gap here is noise on an
  ~800ms call, not evidence of a hit. `reproducibility`/`badge.json` (which shares
  `hubReproducibilityFor()`'s 5-minute cache) show the real effect: cold 2-11ms, warm ~1ms — the
  second call is answered from the in-process cache, not recomputed. None of the four unlimited
  routes shows any warm-vs-cold improvement worth calling a cache hit.

In short: on this tree, right now, the P1-03 finding reproduces at a scale the original 300x3000
adversarial fixture never exercised (50 projects instead of one) — `/healthz` at 52 seconds instead
of 9.8 — and the fix it names (a limiter plus a short per-project memoization on the same four
routes, mirroring `HUB_REPRO_CACHE`) is the change that should move every "**YES**" in the table
above back to "no" and bring the `/healthz` max back under budget. This report does not implement
that fix; it is the before-picture the concurrent fix round can be checked against.

## What this does not cover

- **Buy-competition standings** (`/p/:compId/standings`) has no seeded competition in this
  fixture — only lock-to-earn programs and receipts are built (per the roadmap item's own fixture
  spec). The route 404s honestly and its latency is real, but it is not exercising the
  comp-standings computation path itself.
- **This is one box, one run of each fixture size**, not a distribution across hardware or a
  long soak. The absolute millisecond numbers will differ on Railway's actual production
  instance; the *shape* — unlimited routes serialising on the event loop under concurrent load,
  limited routes bounding volume but not always latency — is what should transfer.
- **No claim is made about what traffic the live CUNA programme (today's only real Hub tenant)
  actually produces.** `docs/HUB_PUBLIC_SURFACES_VERIFY_2026-09-18.md` already estimated the
  live-ledger cost at "closer to 0.1s" per call given today's much smaller CUNA ledger; this
  report's fixture is deliberately far larger (the roadmap item's own 50x200 sizing target) to
  make the shape of the problem visible without needing production-scale data.
