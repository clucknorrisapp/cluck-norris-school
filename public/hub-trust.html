What This Doesn't Prove

THE HUB'S TRUST BOUNDARY · IN PLAIN WORDS

The Project Hub shows what a project promised, who qualified, and the transaction that paid each one — re-checked against Solana in your own browser. This page is the other half: what none of that shows, so nobody reads more into a receipt than it actually proves.
The chain shows what, never why
Solana shows a transfer happened: from which wallet, to which wallet, how much, and when. It never shows intent. We only call a wallet a project's "team" or "creator" when a launchpad's own record confirms it — never from guessing at a pattern.
The funding wallet is the project's, not ours
Every payout on the Hub comes out of the project's own funding wallet, named on its page. Cluck Norris never holds the reward tokens and never fronts them. If a project's funding wallet runs low, its payouts stop — that is the project's balance, not ours.
A hash commits to terms, not to intent
A program version's hash is served by the same server that computes the payout. Recomputing it yourself at /hub/verify proves the server did not change the terms after publishing them. It does not prove the server left out no qualifying wallet when it first worked out who qualifies. That second guarantee needs the hash to be committed on-chain, independently, by the project's own funding wallet — and as of today, no real program has done that yet.
A receipt proves a rule was followed, not that it was fair
A match at /hub/verify proves one thing: the amount paid is exactly what the published rule computes for that wallet. It says nothing about whether the rule itself was reasonable, whether the terms were generous, or whether the project is worth locking with in the first place. Read the terms yourself before you decide any of that.
What a dry run is, and isn't
/hub/demo is a fixture: real Hub code running over made-up addresses, labelled DRY RUN everywhere it appears. A dry-run project page — a real, branded page while terms are still being agreed with a team — is the same in substance: nothing on it can be armed or paid. Either way, nothing is paid, and nothing on a dry-run page counts toward any total the Hub reports.
A reproducibility ratio below 1.0
Each project's reproducibility ratio is the share of its receipts that recompute to the published amount. Below 1.0 does not by itself mean something is wrong — it can mean a receipt kind this tool can't check yet, or inputs that weren't kept on your end. If you see it: open /hub/verify on that specific receipt, keep whatever you fetched, and ask the project directly rather than assume the worst.
The ratio also doesn't yet count every receipt kind — a giveaway row is named as not implemented rather than folded quietly into the number.
What doesn't reproduce yet
Giveaway rows — a sealed-draw giveaway, and the older, pre-Hub Buy Special draw — don't reproduce today. The reproduce tool handles lock-to-earn and buy-competition receipts only; a giveaway kind says so plainly rather than guessing at a number.
The newer per-transfer settlement journal is now the live path for a project paid through the Hub's own payout route — a receipt from that route carries the fuller record the schema documents. CUNA's own payouts, the only real money moving through this today, still run on a separate, older handler that doesn't use it — so the one real receipt you can currently fetch is still the older, single-row shape, and that stays true until CUNA is moved onto the same route.
Four things that still need a human
  • Promotion to production. Some of what this page describes runs on staging today, not yet on the live site.
  • The first on-chain commitment. No real program's hash has been committed on-chain by a funding wallet yet.
  • Real terms, agreed with a project. A dry-run page is a rehearsal until a team signs off on its own numbers.
  • A full run with a real wallet. Locking, qualifying, and getting paid, start to end, with a real wallet.
